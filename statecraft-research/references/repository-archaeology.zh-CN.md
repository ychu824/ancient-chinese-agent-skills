# 仓库考古

调研对象是代码库或系统时读这个：要在一个现有项目里找优化点、研究贡献或空白。英文版是 `repository-archaeology.md`。

夫地形者，兵之助也……知此而用战者必胜，不知此而用战者必败（《孙子·地形篇》）。没读过系统就提改动方案，等于在没人探过的地面上行军。

不用乡导者，不能得地利（《孙子·军争篇》）。仓库里的乡导是 issue、PR 和提交历史：它们记着什么试过、什么被否了、为什么。

## 提建议之前先确定的事

1. **钉住版本**。记下仓库、commit hash 和日期。项目变得快，一条发现几周内就可能失效；不带版本的发现没法复核。
2. **找到执行路径**。针对要看的模型或 workload，找出入口，从输入跟到输出，写下这条路径上的文件和函数。
3. **摸清已有的机制**。在你可能要动的那一块，列出现有的调度、batching、chunking、编译、缓存、阶段间传输等机制。和现有机制重复的想法不算想法。
4. **读项目自己的记录**。在 open 和 merged 的 PR、open 和 closed 的 issue、benchmark、近期提交里搜这一块，找进行中的工作、被拒的尝试和公开的 roadmap。托管平台的 API 和搜索用不了时，用下面的退路。
5. **把观察到的和设想的分开**。每个候选瓶颈都说明它属于哪一种：
   - 测量：你跑过，或项目公布了测量结果，并写明条件
   - 读到：代码里看得出来，附上行号链接
   - 假设：从设计上看合理，但没有确认

## 代码库的入口

水因地而制流，兵因敌而制胜（《孙子·虚实篇》）。`scouting.zh-CN.md` 里的六个入口是为文献调研写的。问题是"在这个项目里能贡献什么、修什么、优化什么"时，改用下面这六个。用几个仍由档位决定。

| 入口 | 问的问题 |
|---|---|
| 按 tracker | 项目自己说想要什么（label、roadmap、RFC、tracking issue），哪些已经有人认领 |
| 按代码自己的债 | 项目自己的工具说哪些还没做完：checker 的 allowlist 和 ratchet 预算、CI 里跳过的 hook、没有任何 CI job 会选中的测试、还没启用的 lint 规则、文档里已经失效的链接和路径 |
| 按反面 | 被拒或停滞的 PR、维护者否掉的改动、和当前代码矛盾的 issue |
| 按流程 | 贡献规则、改动必须带的证据、review 和合并怎么排队、要等多久 |
| 按上游和邻居 | 上游项目或同类项目已经修掉或采用、而这个项目还没有的东西 |
| 按执行路径 | 性能或正确性问题：从输入到输出的路径，即上面的第 2、3 条 |

有两个交叉检查值得做。label 和 open issue 只是一种说法：把它和当前代码、关联的 PR 对过，才能算作还没人做的活。在代码里找到的缺陷，在查过项目记录里有没有人正在修之前，只是候选。

## 托管平台的 API 和搜索用不了时

管仲曰：老马之智可用也。乃放老马而随之，遂得道（《韩非子·说林上》）。向导问不到，就跟着项目留在 git 里的踪迹走。

- **Open 和近期的 PR**。GitHub 把每个 PR 发布成 git ref。用 `git ls-remote <remote> 'refs/pull/*/merge'` 列出来，fetch 到一个单独的 bare repo 里，把每个快照里你打算改的文件和钉住的版本比对。某个快照在你要改的那几行已经不一样，就是别人在做同一件事。其他平台有名字不同的等价 ref。
- **已合并的历史**。在足够深的 clone 上用 `git log --grep` 和 `git log -S<字符串>`。shallow clone 回答不了某样东西何时被删、为什么删。
- **只 fetch**。这些操作不写远端，对公开仓库也不需要凭据。

这条退路看不到的东西：issue 和 review 讨论；没有 merge ref 的 PR（和基线分支冲突的那些）；还没 push 的工作。后来被关闭的 PR，merge ref 也可能还留着。结论写成"N 个 PR 快照里未见"，说明上面哪些盲区适用，并把 tracker 搜索留给用户在动手前自己做。

## 交回的内容

每条针对代码库的建议：

| 字段 | 内容 |
|---|---|
| 位置 | 实现路径上的文件和行号链接，对应钉住的版本 |
| 现状 | 现有机制，一两句话 |
| 项目里的相关历史 | 涉及它的 issue 和 PR，以及各自的状态；tracker 搜不了时，写明查重是怎么做的、这种做法看不到什么 |
| 证据 | 测量 / 读到 / 假设，以及哪些还没测 |
| 拟议的改动 | 会有什么不同 |

填不出"位置"的建议，还不能参与排序。

## 注意

- 除非用户要求且环境允许，不要运行下载下来的代码。摸清路径通常读代码就够了。
- 只抽看了 README 和几个 issue，属于 pilot，要按 pilot 报告。
- 没测量过的优化机会不是项目的缺陷。把它写成假设，也不要替用户去开 issue 或 PR。
